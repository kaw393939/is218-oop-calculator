## Type and run

### 6A — Publish and verify

Type `.github/workflows/tests.yml` from the worked branch, then write your own README using the [assignment criteria](https://github.com/kaw393939/is218-oop-calculator/blob/main/docs/assignment.md). YAML indentation expresses structure.

| Section | Meaning |
| --- | --- |
| `on` | Run on pushes, pull requests, or manual requests. |
| `permissions` | Give the job read access to repository contents. |
| `jobs` and `runs-on` | Run the work on a fresh Ubuntu runner. |
| `strategy.matrix` | Repeat it for Python 3.11, 3.12, 3.13, and 3.14. |
| `uses` | Invoke a reusable action, such as installing Python. |
| `run` | Execute a shell command. |

`${{ matrix.python-version }}` selects the version for each job. The steps download code, install Python, install requirements, and run pytest. `pytest.ini` supplies the coverage gate. This neither deploys the app nor configures required merge checks.

Run `python -m pytest` locally. Create an empty repository in your GitHub account, then publish from **your solution folder**:

```bash
git add .github/workflows/tests.yml README.md
git commit -m "Stage 6: automate calculator checks"
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
git push -u origin main
```

Replace the placeholders. If origin already points to your solution, skip adding it again; inspect it with `git remote -v`. Use your own repository rather than the instructor's reference. Authentication prompts are part of GitHub access, not calculator behavior.

Open **Actions → Calculator tests**. Check each Python-version job. If a job fails, open the failing step and locate the first useful assertion or exception; the final exit-code message alone does not explain the cause.

### Read a failed run

Here is an **illustrative abbreviated log**, not a claim that the current reference CI is failing:

```text
Step: Run tests and enforce coverage
FAILED tests/test_calculation.py::test_add
    assert result == 16
E   assert 15 == 16
Process completed with exit code 1.
```

| Evidence | Interpretation | Next action |
| --- | --- | --- |
| Test path and `test_add` | The failing behavior is identified. | Run `python -m pytest tests/test_calculation.py -k test_add`. |
| Expected 16, received 15 | Compare the test inputs and requirement before changing anything. | For Add(10, 5), the expectation should be 15. |
| Exit code 1 | The step failed; this is the consequence. | Fix the cause, rerun locally, commit, and push. |

If the log instead says coverage is below 100%, read the `Missing` column. A coverage failure and an incorrect-result assertion are different problems. An installation failure happens before either and belongs to the dependency/setup step.

**Checkpoint 6A:** local tests pass, all four jobs are green, and you can identify the useful evidence in a failure log. Pause here before the design reading.

## Explain and experiment

### 6B — Reflect and transfer

Read [the bigger picture](https://github.com/kaw393939/is218-oop-calculator/blob/main/docs/bigger-picture.md). Use the history, pattern comparisons, and SOLID discussion to name ideas you have already used. Memorizing dates and implementing every named pattern are not required.

Write a short reflection in your README:

1. Where would Multiply belong? Include changes to registration, help, and tests; explain why History needs no multiplication logic.
2. What contract could email and text-message notification objects share through `send()`?
3. What design knowledge transfers to another language, and what syntax or runtime rules would you still need to learn?

### Build something independently

Ask a classmate to use your README, or follow it yourself from a fresh clone in a separate folder with a new environment. Record one confusing instruction and improve it. Also explain how you would investigate a run in which tests pass but coverage fails; no worked answer is supplied. Do not intentionally publish broken coursework just to produce a red check.

Optional multiplication work belongs after the baseline passes. It should add meaningful assertions and is not a substitute for the reflection.

## Check your understanding

1. Why must CI install packages when the app uses only the standard library?
2. How can the log distinguish an assertion failure from an installation failure?
3. Does a shared design vocabulary imply identical grammar across languages?
